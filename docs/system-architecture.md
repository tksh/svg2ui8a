# System Architecture: `svg2ui8a`

This file is the **third** document an AI agent reads (after
`AGENTS.md` and `docs/project-constitution.md`). It describes the
package layout, the data flow, and the Wasm boundary.

The human owns this file. If the agent believes something here is
wrong, the agent must surface the issue, not rewrite the file.

## 1. Package layout

`svg2ui8a` is a single JSR package. Internally it is a workspace
with two Rust crates and one TypeScript entry point:

```
svg2ui8a/
├── jsr.json
├── README.md
├── LICENSE
├── deno.json                    # Deno tasks, fmt config, lint config
├── src/
│   └── mod.ts                   # The TS entry point (re-exports)
├── crates/
│   ├── svg2usvg/                # Wasm crate, usvg only
│   │   ├── Cargo.toml
│   │   ├── src/lib.rs
│   │   └── tests/
│   └── (future) usvg2rgba/      # Reserved for a future package, NOT this one
└── assets/
    └── svg2usvg_bg.wasm         # Built artifact, vendored
```

There is no `crates/usvg2rgba/` in this package. The path above is
**reserved** as a comment only. Adding it is a separate task.

## 2. JSR subpath exports

`svg2ui8a` exposes the following subpaths:

| Subpath      | What it loads                         | Wasm size |
|--------------|---------------------------------------|-----------|
| `svg2ui8a`   | Full entry point (currently equals `./usvg`) | Small  |
| `svg2ui8a/usvg` | The `usvg`-only build             | Small     |

Both currently resolve to the same Wasm artifact because there is
only one operation. The subpath exists so that future additions
(`./renderer` for `usvg2rgba`) can be added without breaking
existing imports.

## 3. Wasm split: why usvg only

The Wasm binary built for this package depends on **only** `usvg`
and `postcard`. It does **not** depend on `resvg`, `tiny-skia`,
`png`, or any other rasterization or encoding crate.

### 3.1 Why

`svg2ui8a`'s job is to produce a `Uint8Array` from an SVG string.
The work it does is:

1. Parse the SVG with `usvg` (XML, CSS, attribute normalization,
   reference resolution).
2. Serialize the resulting `usvg::Tree` with `postcard`.

That is the entire pipeline. There is no geometry walk, no pixel
allocation, no encoding. The Wasm module never touches a single
pixel.

Including `resvg` / `tiny-skia` / `png` would inflate the Wasm
binary by roughly 2.5x to 3x for zero benefit. Every byte in the
Wasm binary is downloaded, compiled, and instantiated on first
load, and then held in memory for the life of the isolate. There
is no reason to pay that cost for code that is never called.

### 3.2 How the split stays clean at the Cargo level

```toml
# crates/svg2usvg/Cargo.toml
[package]
name = "svg2usvg"
version = "0.1.0"
edition = "2021"

[lib]
crate-type = ["cdylib", "rlib"]

[dependencies]
usvg = "0.34"
postcard = "1.0"
wasm-bindgen = "0.2"
serde = { version = "1.0", features = ["derive"] }

[dev-dependencies]
wasm-bindgen-test = "0.3"
```

That is the entire dependency list. No `resvg`, no `tiny-skia`, no
`png`, no `image`.

## 4. The Rust API

`crates/svg2usvg/src/lib.rs`:

```rust
use usvg::Tree;
use wasm_bindgen::prelude::*;

#[wasm_bindgen]
pub fn svg2usvg(svg: &str) -> Result<Vec<u8>, JsError> {
    let tree = Tree::from_str(svg, &usvg::Options::default())
        .map_err(|e| JsError::new(&format!("usvg parse error: {e}")))?;

    postcard::to_stdvec(&tree)
        .map_err(|e| JsError::new(&format!("postcard encode error: {e}")))
}
```

That is the entire `lib.rs`. The crate does not export anything
else.

### 4.1 Build

Build command (for the agent's reference; the exact command lives
in `scripts/build.ts`):

```bash
cd crates/svg2usvg
wasm-pack build --release --target deno
```

Output is `crates/svg2usvg/pkg/svg2usvg_bg.wasm` and
`crates/svg2usvg/pkg/svg2usvg.js`. The build script copies the
Wasm to `assets/svg2usvg_bg.wasm` and writes the JS glue to
`src/usvg.ts`.

## 5. The TypeScript surface

`src/mod.ts`:

```ts
export { svg2usvg } from "./usvg.ts";
```

`src/usvg.ts` (auto-generated by `wasm-pack`, then committed):

```ts
// Do not hand-edit. Re-run scripts/build.ts to regenerate.
import init, { svg2usvg } from "../assets/svg2usvg_bg.wasm";

let initialized = false;

async function ensureInit(): Promise<void> {
  if (initialized) return;
  await init();
  initialized = true;
}

export async function svg2usvg(svg: string): Promise<Uint8Array> {
  await ensureInit();
  return svg2usvgRaw(svg);
}
```

The agent must **not** hand-edit `src/usvg.ts`. If the file needs
to change, regenerate it via the build script.

## 6. Data flow

```
┌─────────────────────────────────────────────────────────────────┐
│ Consumer code (Deno / browser)                                   │
│                                                                  │
│   import { svg2usvg } from "jsr:@your-org/svg2ui8a/usvg";       │
│                                                                  │
│   const bytes = await svg2usvg(svgString);                       │
│   const key   = `${VERSION}:${hex(sha256(bytes))}`;              │
└──────────────────────────────┬───────────────────────────────────┘
                               │ "svg string" (UTF-8)
                               ▼
┌─────────────────────────────────────────────────────────────────┐
│ Wasm boundary (svg2usvg_bg.wasm)                                │
│                                                                  │
│   1. usvg::Tree::from_str(svg, &Options::default())             │
│      - XML parse                                                 │
│      - CSS / <style> resolve                                     │
│      - Attribute normalization                                   │
│      - <use> / <defs> reference resolution                       │
│      - returns: usvg::Tree (in Wasm linear memory)               │
│                                                                  │
│   2. postcard::to_stdvec(&tree)                                  │
│      - returns: Vec<u8> (in Wasm linear memory)                   │
│                                                                  │
│   3. wasm-bindgen copies Vec<u8> → Uint8Array (JS heap)         │
│      - one memcpy at the Wasm boundary                           │
└──────────────────────────────┬───────────────────────────────────┘
                               │ Uint8Array (postcard bytes)
                               ▼
┌─────────────────────────────────────────────────────────────────┐
│ Consumer code                                                    │
│                                                                  │
│   - Passes the bytes to crypto.subtle.digest("SHA-256", bytes)   │
│   - Or stores the bytes in a cache (KV, R2, filesystem)         │
│   - Or passes the bytes to a downstream consumer (e.g. a future  │
│     usvg2rgba package)                                           │
└─────────────────────────────────────────────────────────────────┘
```

The Wasm boundary is crossed **once**: the input SVG goes in, the
`Uint8Array` comes out. There is no intermediate JS object, no
JSON, no SVG string, no pixel buffer.

## 7. What the agent should and should not optimize

### 7.1 Worth optimizing

- **Wasm binary size.** Smaller is better. The current
  `usvg` + `postcard` footprint is the minimum; the agent should
  not add anything that inflates it.
- **Wasm cold-start latency.** First-call `await init()` cost.
  The TS wrapper handles this with a single
  `initialized` flag, which is sufficient.
- **Wasm linear-memory-to-JS-heap copy.** This is a memcpy of the
  `Vec<u8>` to the JS `Uint8Array`. There is nothing the agent
  can do about it short of changing the format (which is
  prohibited).

### 7.2 Not worth optimizing

- **SVG parse time inside `usvg`.** This is upstream behavior. Do
  not patch `usvg`. If it is too slow for a specific input,
  surface the issue per `./AGENTS.md` §10.
- **postcard encode time.** This is also upstream. The
  `usvg::Tree` is small relative to the input SVG; encoding
  dominates only for large inputs.
- **The TS wrapper.** The current 10-line wrapper is correct. Do
  not turn it into a class, do not add caching, do not add
  options.

## 8. Failure modes

### 8.1 Malformed SVG

`usvg::Tree::from_str` returns an error. `svg2usvg` rejects the
returned promise. The agent must not swallow the error; the
caller decides what to do.

### 8.2 Out-of-memory

If the SVG is pathologically large, the Wasm linear memory may
exhaust. `wasm-bindgen` will surface this as a JS exception. The
caller is expected to handle it; the agent must not pre-emptively
cap input size inside `svg2ui8a`.

### 8.3 Version skew

If the consumer's Wasm binary does not match the TS glue (e.g.
because the Wasm was rebuilt but `src/usvg.ts` was not
regenerated), behavior is undefined. The build script's job is to
keep them in sync; the agent must not bypass it.
